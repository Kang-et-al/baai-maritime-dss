## 2. 프로젝트 배경과 기준

- 저장소: https://github.com/Kang-et-al/baai-maritime-dss
- 기준 태그: v0.2.0-draft.1
- 기준 배포와 결과: https://github.com/Kang-et-al/baai-maritime-dss/releases/tag/v0.2.0-draft.1
- 목적: 부산 → 홍콩 운항을 태풍 예측과 함께 계획하는 교과목용 의사결정지원시스템(DSS).
- 선박 1척, 18해리 격자, 해상 노드 2,286개와 방향 아크 8,600개를 사용한다.
- 3시간마다 다음 도달 노드를 선택하고, 내부 계산은 15분 단위로 한다.
- 1단계는 주변 후보 노드까지의 최소 실행비용을, 2단계는 후보에서 목적지까지의 시나리오별 최소 잔여비용을 구한다.
- 두 단계를 통합해 현재 실행비용 + 미래 평균/CVaR 종합점수를 최소화한다. 경로 계산은 DP를 사용한다.
- 정본 설정은 configs/baseline.json, mean-CVaR 위험 가중치 0.5 / CVaR 수준 0.8이다.
- 태풍 생성기는 trend-path-intensity-3x3-v1, 경로 3개 × 강도 3개 = 동일 확률 9개 시나리오다.
- 실제 태풍은 고정된 시나리오를 따라 실현되고, 예측은 롤링 시점의 관측에 따라 재생성된다.
- 태풍 영향 반경은 강도에 비례한다. 기상 API나 AI API를 호출하지 않는다.
- 별도의 최적화 솔버나 유료 클라우드 계산 환경은 필요 없다.

이 요약보다 현재 저장소의 코드와 최신 기준 문서를 우선해서 실제 구현을 확인해라.
모형·태풍 생성 규칙을 개선하는 일은 내가 요청한 경우에 진행한다.

## 3. 처음 설치하고 프로젝트를 이해하는 순서

1. 기존 폴더와 작업 파일을 확인해라. 이미 파일이 있는 폴더를 덮어쓰지 마라.
   이미 저장소가 있다면 원격 주소와 수정 중인 파일을 확인한 뒤 재사용 여부를 판단해라.
2. 새 설치라면 위 비공개 저장소를 Git으로 복제해라. GitHub Desktop을 사용해도 된다.
   ZIP 다운로드만으로 시작하면 Git 이력이 없으므로 팀 개발에는 Clone을 우선해라.
3. 먼저 아래 문서를 읽고, 내가 이전 대화를 공유하지 않아도 작업할 수 있도록 맥락을 정리해라.
   - AGENTS.md
   - README.md
   - PROJECT_CONTEXT_TEAM.md
   - docs/BASELINE.md
   - docs/SETUP.md
   - docs/TEAM_GUIDE.md
   - docs/EXPERIMENTS.md
   - docs/SHARED_VALIDATION.md
   PROJECT_CONTEXT.md는 과거 개인 단계의 기록이므로 최신 팀 상태와 혼동하지 마라.
4. 최초 기준 확인은 v0.2.0-draft.1에서 진행해라.
   수정이 필요하면 해당 태그에서 experiment/<팀식별자>/onboarding 같은 새 브랜치를 만들어라.
   기존 작업을 강제 초기화하거나 main에 직접 덮어쓰지 마라.
5. Python 3.12.x를 확인하고 저장소 폴더에 .venv를 만들어라.
   초기 설치는 Python 3.12로 scripts/bootstrap.py를 실행한다.
   Windows에서는 setup_windows.bat을 사용할 수 있다.
   NumPy 2.3.5 / Pillow 12.3.0은 requirements-lock.txt로 설치한다.
   다른 사람의 PC 경로나 Codex 내장 Python 경로를 코드에 넣지 마라.
6. 이후 명령은 저장소 최상위 폴더에서 .venv의 Python으로 실행해라.
   Windows: .venv/Scripts/python.exe
   macOS/Linux: .venv/bin/python
   아래 예시의 python은 이 실행 파일을 뜻한다. 최초 bootstrap 실행만 설치된 Python 3.12를 사용한다.
7. 다음 검증을 실행하고 성공/실패를 실제 출력으로 확인해라.

   python -m unittest discover -s tests -v
   python -m maritime_sim baseline
   python scripts/verify_release.py --ref v0.2.0-draft.1

기준 초안은 단위·회귀 검증 21개와 기준 파일 해시 24개를 확인한다. 이후 버전은 검증 수가 늘어날 수 있다.
개발 중 baseline 명령이 changed를 반환하는 것은 기준 소스와 달라졌다는 뜻이다.
검증을 통과시키려고 baseline.lock.json이나 시나리오 fixture를 재작성하지 마라.
문제가 생기면 원인을 설명하고 필요한 부분만 고쳐라. 검증을 생략하고 완료했다고 보고하지 마라.

## 4. 최초 예시 실행: 한 스텝만 진행

새 출력 폴더를 정해 아래 형식으로 실행해라.

python -m maritime_sim run --config configs/baseline.json --experiment live --steps 1 --output outputs/<팀식별자>_baseline_live_01

실행 후 해당 폴더의 dashboard.html을 브라우저로 열어라.
현재 위치, 누적 비용/연료, 실제 항적, 예상 태풍 경로·영향권, 예상 운항 경로가 어디에 표시되는지 짧게 설명해라.
기준 설정의 첫 스텝은 출항 후 3시간, N3122, 연료 약 1.5톤이 참고값이다.
실제 기록과 비교하고 차이가 있다면 원인을 확인해라.

이어서 진행하라는 요청을 받으면 같은 폴더에 다음과 같이 추가 실행한다.

python -m maritime_sim run --resume --steps 3 --output outputs/<팀식별자>_baseline_live_01

--steps 3은 기존 상태에서 세 스텝을 추가한다는 뜻이다.
이어하기에는 --config를 다시 주지 않는다. 저장된 설정을 사용한다.
코드·데이터·설정이 바뀌어 이어하기가 거부되면 체크를 우회하지 말고 새 실험을 만들어라.

## 5. 내가 요청할 때 수행할 완주 재생 실험

내가 “기준 완주 재생 실험을 실행해줘”라고 요청하면, 새 폴더에서 실행해라.

python -m maritime_sim run --config configs/baseline.json --experiment replay --output outputs/<팀식별자>_baseline_replay_01

replay는 도착 또는 종료 조건까지 진행한다. --steps를 함께 주지 않는다.
실행 후 dashboard.html을 열고 시간 슬라이더로 과거 시점의 상황을 되돌아보는 법을 알려줘라.
최종 status가 arrived인지 확인하고, 계획 불가능/시간 제한 종료를 성공 도착으로 보고하지 마라.

기준 배포의 참고 결과:
- 44스텝 / 132시간에 홍콩 도착.
- 거리 1,584해리 / 대기 2시간 / 연료 약 76.206톤.
- 실제 비용 약 111,723.43달러 / 지연 0시간.

매 시점의 mean-CVaR 평가 점수는 그때의 미래 계획을 평가하는 값이며, 최종 실제 비용과 다르다.
운영체제·수치 계산에 따른 작은 차이를 구분하고, 픽셀이나 소수점 전체의 동일성을 요구하지 마라.
기준 결과 ZIP은 배포 페이지에서 내려받아 압축을 풀면 다시 계산하지 않고도 확인할 수 있다.

주요 출력:
- config.json: 병합된 전체 실행 설정.
- manifest.json: Git 커밋·수정 여부·설정/소스 해시·라이브러리 버전.
- state.json: 현재 상태와 누적 KPI.
- steps/: 시점별 관측·예측·후보 평가·선택·실행.
- dashboard.html: 시간 슬라이더가 있는 대시보드.
- archive.html / figures/ / summary.csv: 그림 모음·시점별 이미지·요약 표.

## 6. 실험 조건이나 코드를 바꾸는 방법

내가 바꾸려는 내용을 먼저 구분해라.
파라미터만 바꾸는 실험이면 configs/experiments/에 별도 JSON을 만들고, 구현 변경이 필요할 때 관련 코드를 수정해라.

예를 들어 “평균 비용만 고려하는 경우를 비교해줘”라고 요청하면:
1. experiment/<팀식별자>/mean-only 같은 작업 브랜치를 만든다.
2. configs/experiments/<팀식별자>_mean_only.json에 아래 설정을 작성한다.

   {"risk": {"lambda": 0.0}}

3. 생략한 항목은 기본 설정에서 병합되는지 확인한다. baseline.json은 수정하지 않는다.
4. 필요한 검증을 하고, 새 설정/코드를 로컬 Git 커밋으로 기록한다.
5. 수정·미추적 파일이 남아 있지 않은 상태에서 새 출력 폴더로 실험한다.
   Git 커밋은 내 PC에 버전을 저장하는 것이며, GitHub 업로드와는 별개다.
6. 해당 설정을 --config로 지정해 실행하고 기준 결과와 비교한다.

위험 가중치를 바꿔도 최종 경로나 KPI가 같을 수 있다. 다른 결과를 만들기 위해 기준을 임의로 바꾸지 마라.
태풍 생성기나 비용 구조를 바꾸라는 요청이라면 변경 범위와 기존 기준과의 차이를 문서에 남겨라.
전체 항해는 내가 요청했을 때만 실행하고, 단순 코드 수정에는 필요한 검증부터 수행해라.

## 7. Git으로 버전과 결과를 공유하는 절차

운영 원칙:
- main: 팀이 받아들인 최신 코드.
- v0.2.0-draft.1: 보존하는 최초 기준 버전.
- feature/<팀식별자>/<주제>: 기능 변경.
- experiment/<팀식별자>/<주제>: 실험 설정이나 독립 변형.

새 일반 작업은 수정 중인 파일을 보존한 뒤 최신 main에서 브랜치를 만든다.
기준 태그와 정확히 비교하는 실험은 해당 태그에서 브랜치를 만든다.
어느 기준에서 출발했는지 결과 설명에 명시해라.

공유할 실험은 다음 순서로 관리해라.
1. 설정/코드 변경 → 검증 → 로컬 커밋.
2. 작업 폴더가 깨끗한 상태에서 실험 실행.
3. 결과 등록 및 ZIP 생성.

   python scripts/register_result.py --run outputs/<실험폴더> --id <팀식별자>-<주제>-<고유번호>

4. results/index.csv와 변경 설명을 후속 커밋.
5. 내가 업로드를 허용했다면 해당 작업 브랜치만 Push하고 PR을 생성.
6. 주요 결과 ZIP은 실제 실행 커밋을 가리키는 새 태그의 Release에 첨부.
   새 태그/Release 생성은 내가 요청하거나 업로드 범위에 포함한다고 명시한 경우 수행해라.
   기존 기준 태그/Release는 덮어쓰지 마라. 결과 색인에 공유 링크도 기록해라.

등록 스크립트는 dist/에 ZIP을 만든다. 실행 당시 코드가 미커밋 상태였다면 기본적으로 등록을 거부한다.
이 문제를 manifest 수정이나 --allow-dirty로 자동 우회하지 마라.
원칙적으로 커밋 후 새 실험을 실행한다. 개발 중 결과를 공유하려는 의도가 명확할 때만 예외를 설명해라.

Git에 올릴 것은 소스·설정·작은 데이터·문서·결과 색인이다.
.venv/, outputs/, work/, dist/와 개인 문서·비밀키를 강제로 추가하지 마라.
PR에는 변경 목적, 변경한 모형/파라미터, 검증, 실험 결과와 해석, 남은 한계를 작성해라.
PR을 만들었다고 main에 병합된 것은 아니다. main 병합은 팀의 검토 절차를 따른다.
강제 Push, 기준 태그 이동, 다른 사람 브랜치 삭제는 하지 마라.

처음 Git 작성자 설정이 필요하면 내 정보를 확인하고 이 저장소에만 설정해라.
GitHub 인증은 내가 직접 처리하도록 하고 저장소 접근이 막히면 초대/로그인 계정을 확인해라.

## 8. 매 작업 후 나에게 알려줄 내용

다음 사항을 짧게 정리해라.
- 실제로 완료한 작업과 실행하지 않은 작업.
- 로컬 프로젝트 폴더, 현재 브랜치와 커밋, 사용한 기준 버전.
- 실행 환경과 검증 결과.
- 실험 출력 폴더와 열어볼 dashboard.html.
- 변경한 설정/코드와 기준 대비 차이.
- GitHub 업로드 여부와 PR/Release 링크, 아직 필요한 사용자 작업.

다음 대화나 다른 AI에서도 이어갈 수 있도록 필요한 변경 이력을 docs/CHANGELOG.md에,
현재 구조·남은 작업을 PROJECT_CONTEXT_TEAM.md에 기록해라.
실험 재현을 위한 문서 변경은 가능하면 실행 전 커밋하고, 결과를 설명하는 변경은 실행 후 후속 커밋으로 남겨라.
전체 작업에 이전 개인 대화나 담당자의 PC 폴더가 필요하지 않도록 저장소 안의 자료로 설명해라.

# 설치 후 내가 사용할 후속 요청 예시

- “지금 실시간 실험에서 세 스텝 더 진행하고, 태풍 때문에 선택이 어떻게 바뀌었는지 설명해줘.”
- “기준 설정으로 완주 재생 실험을 실행하고 시간 슬라이더 대시보드를 열어줘.”
- “평균 비용만 고려하는 설정을 별도 브랜치에 만들고 기준 실험과 비교해줘.”
- “현재 변경을 검증하고 로컬 커밋해줘. 아직 GitHub에는 올리지 마.”
- “지금 작업 브랜치를 GitHub에 올리고 PR을 만들어줘. main에는 아직 병합하지 마.”
- “이 완주 결과를 공유할 버전으로 남겨줘. 실행 커밋을 가리키는 새 태그와 Release를 만들고 결과 ZIP을 첨부해줘.”
