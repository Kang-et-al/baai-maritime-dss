# 모델 개선과 버전 업로드 지침

## 현재 구조와 보존 범위

초기 모델은 `v0.2.0-draft.1` 태그와 같은 이름의 Release로 보존한다.
main에 개선 코드를 반영해도 이 태그가 가리키는 초기 소스는 그대로 남는다.
Git은 매번 폴더 전체를 다른 이름으로 올리는 대신 커밋 이력으로 파일 변경을 관리한다.

| 구분 | 역할 | 언제 만들어지는가 |
|---|---|---|
| 커밋 | 특정 시점의 소스 기록; 실제 재현 식별자 | 로컬에서 commit할 때 |
| 작업 브랜치 | 개선/실험 작업의 진행 경로 | 작업을 시작할 때 |
| main | 팀이 받아들인 최신 공통 코드 | PR을 검토하고 병합할 때 |
| 태그 | 이름 붙여 보존하는 특정 커밋 | 명시적으로 tag를 만들 때 |
| Release | 태그 설명과 결과 ZIP을 전달하는 배포 페이지 | 별도로 Release를 만들 때 |

Push는 로컬 커밋/브랜치를 GitHub에 올리는 동작이다. 새 버전 번호·태그·Release를 자동 생성하지 않는다.
브랜치에 Push만 하면 main은 바뀌지 않는다. main에 병합해도 과거 커밋과 초기 태그로 돌아가 확인할 수 있다.
저장소의 태그 불변성은 현재 팀 운영 규칙이며 기술적 강제 잠금은 아니다. 기존 태그를 이동·삭제하거나 강제 Push하지 않는다.

## 작업마다 따를 절차

1. 현재 폴더·브랜치·미커밋 변경을 확인한다. 기존 변경을 강제로 초기화하지 않는다.
2. 일반 개선은 최신 main, 초기 모델과의 독립 비교는 v0.2.0-draft.1을 출발점으로 선택한다.
3. `feature/<이름>/<주제>` 또는 `experiment/<이름>/<주제>` 작업 브랜치를 만든다.
4. 파라미터 실험은 configs/experiments/에 새 JSON으로, 구현 변경은 필요한 코드에 반영한다.
5. 필요한 검증과 작은 실행을 한다. 변경 이력과 인계 문서를 작성하고 소스/설정을 커밋한다.
6. 공유할 실험은 미커밋·미추적 변경이 없는 상태에서 새 outputs 폴더에 실행한다.
7. 결과의 manifest에 저장된 실제 실행 커밋과 설정/코드 해시를 확인한다.
8. 결과 등록 후 results/index.csv와 해석 문서를 별도의 후속 커밋으로 남긴다.
9. 사용자가 업로드를 요청했다면 작업 브랜치를 Push하고 PR을 만든다. main 병합은 별도 요청/팀 검토 후 진행한다.

실험 도중 소스가 바뀌면 새 실험을 시작한다. 기존 실험 manifest를 고쳐 새 버전인 것처럼 표시하지 않는다.
PR 병합 없이도 작업 브랜치와 태그로 독립 모델 버전을 보존·공유할 수 있다.
충돌이 있으면 관련 변경을 비교해 해결하고 검증한다. 다른 사람의 작업을 덮어쓰기 위한 강제 Push는 하지 않는다.

## 버전 이름

| 상황 | 예시 | 규칙 |
|---|---|---|
| 최초 공유 기준 | v0.2.0-draft.1 | 기존 태그와 Release 유지 |
| 기능·모델·알고리즘 개선 | v0.3.0 | 팀이 채택한 의미 있는 개선 배포 |
| 오류 수정 배포 | v0.3.1 | 기존 기능의 수정 |
| 큰 호환성 변경 | v1.0.0 등 | 설정/결과 호환성에 큰 영향이 있으면 팀과 버전 범위 결정 |
| 독립 실험 모델 | v0.3.0-minsu-routing.1 | 실험자/주제/회차를 포함하고 Pre-release로 배포 |
| 안내문만 수정 | 새 버전 없이 문서 커밋 | 매 커밋마다 Release를 만들 필요 없음 |

위 번호는 예시다. 원격 태그를 확인하고 아직 쓰지 않은 번호를 선택한다.
패키지의 __version__도 자동 증가하지 않는다. 코드 배포 시 선택한 배포 버전에 맞게 명시적으로 갱신한다.
독립 실험은 태그와 실행 커밋을 우선 식별자로 사용한다.

## 재현용 태그와 결과 Release 만들기

사용자가 버전 배포까지 요청했을 때만 다음 절차를 실행한다.

1. 배포할 소스/설정을 커밋하고 검증한다. 공유 실험을 깨끗한 작업 상태에서 실행한다.
2. 결과 manifest의 `git.commit`을 기록한다.
3. 새 태그는 **그 실제 실행 소스 커밋**을 가리키게 만든다. 결과 색인만 추가한 후속 커밋과 구분한다.
4. 해당 태그를 Push하고 Release를 만든다. 실험용은 Pre-release로 표시한다.
5. register_result.py로 만든 ZIP을 첨부하고, Release에 기준 버전·실행 커밋·설정·변경점·검증·실제 KPI·한계를 적는다.
6. results/index.csv에 Release 링크를 남기고 결과 문서와 함께 후속 커밋/PR로 공유한다.
7. docs/VERSIONS.md에 새 버전과 링크를 추가한다. 초기 태그와 Release는 갱신하지 않는다.

현재 최초 Release는 실험 실행 커밋 69fc1a6 이후 결과 문서까지 포함한 d593c19에 태그를 만들었다.
두 커밋의 모형/설정/데이터/렌더러 해시는 같으며 기존 배포 설명에 기록되어 있다. 앞으로는 위 절차로 실행 커밋을 직접 태그한다.
PR 병합 과정에서 커밋이 바뀌었다면 기존 결과를 병합 커밋의 실행 결과로 바꾸어 표기하지 않는다.
병합 버전 자체를 검증하려면 그 커밋에서 새 실험을 실행한다.

## 원래 기준과 새 버전의 구분

- manifest의 git.commit은 실제 실행한 코드 버전이다.
- git.baseline_ref는 현재 원래 비교 기준인 v0.2.0-draft.1을 뜻한다. 새로운 실행 버전 이름을 뜻하지 않는다.
- baseline_id는 모형/설정 기준 ID다. 소스 개선마다 자동으로 바뀌지 않으므로 이것만으로 버전을 구분하지 않는다.
- configs/baseline.lock.json은 최초 배포 파일 확인용이다. 개발 중 changed는 예상되는 상태다.
- 개선 모델의 새 태그를 만들었다고 원래 baseline lock을 자동 갱신하지 않는다.
- 새 모델을 팀의 새로운 공통 기준으로 승격할 때는 별도 합의로 기준 ID/정본/lock/회귀 검증/참조 문서를 함께 갱신한다.

## AI에게 전달할 업로드 요청

> 현재 로컬 변경을 확인하고 기존 작업을 보존해줘. docs/VERSIONING.md와 AGENTS.md를 읽어줘.
> 이번 변경은 [변경 목적]이고 출발 기준은 [최신 main / 특정 태그]야.
> 적절한 작업 브랜치에서 필요한 검증을 하고 소스·설정을 커밋해줘.
> [실험 요청이 있다면 조건과 실행 범위]로 새 실험을 실행하고 결과를 등록해줘.
> 작업 브랜치를 GitHub에 Push하고 PR을 만들어줘. main 병합은 아직 하지 마.
> 기존 v0.2.0-draft.1과 다른 사람의 브랜치는 보존해줘.

배포도 원하면 다음을 덧붙인다.

> 이 결과를 재현 가능한 독립 버전으로도 보존해줘. 사용되지 않은 태그 이름을 정하고,
> 실제 실행 커밋을 가리키는 새 태그와 Release를 만들어 결과 ZIP과 설명을 연결해줘.
> docs/VERSIONS.md에 버전을 등록해줘.
